# IAM Proxy Service (Keycloak Integration Demo)

## Концепция

Проект демонстрирует паттерн безопасной интеграции микросервисов с Identity Provider (Keycloak)
через слой проксирования. Фронтенд или клиентское приложение не обращается к Keycloak напрямую:
прокси скрывает `client_secret`, централизует логику аутентификации и валидации JWT, а также
извлекает роли пользователя для последующего контроля доступа (RBAC). Такой слой позволяет
заменить IdP без изменения клиентского кода и не выпускать Keycloak во внешний периметр.

## Как это работает под капотом (Deep Dive)

Взаимодействие разделено на два ключевых этапа: получение токена (аутентификация) и его проверка (авторизация).

### 1. Аутентификация (`POST /login`)
1. Клиент отправляет `username` и `password` в открытом виде (по HTTPS) на наш прокси.
2. Прокси **не проверяет пароль сам** и **не хранит хэши**. Он берет эти данные и добавляет к ним `client_id` и `client_secret` (которые знает только он).
3. Прокси отправляет POST-запрос в Keycloak по эндпоинту `/token` с `grant_type=password`.
4. **Keycloak берет на себя всю криптографию**: находит пользователя в своей БД, достает его соленый хэш пароля (например, PBKDF2 или Argon2), хэширует полученный от прокси пароль и сравнивает результаты. 
5. Если пароли совпали, Keycloak генерирует JWT (JSON Web Token) и подписывает его своим приватным ключом (RS256). Прокси возвращает этот токен клиенту.

*Почему это безопасно:* Фронтенд не знает `client_secret`. Если злоумышленник перехватит пароль, он не сможет получить токен напрямую от Keycloak, так как Keycloak не принимает запросы от неизвестных клиентов без секрета. Прокси выступает как "щит".

### 2. Авторизация и валидация (`GET /me`)
1. Клиент передает полученный JWT в заголовке `Authorization: Bearer <token>`.
2. Прокси берет токен и идет в Keycloak по эндпоинту `/certs`, чтобы забрать **публичный ключ** (JWKS).
3. Прокси проверяет **подпись токена** этим публичным ключом. Если токен подделан (изменен хотя бы один символ в payload), подпись не сойдется, и прокси вернет 401.
4. Прокси также проверяет поле `iss` (issuer), чтобы убедиться, что токен выпущен именно нашим Keycloak, а не сторонним сервером.
5. Если проверки пройдены, прокси парсит payload и достает роли (`iam-user`) для дальнейшего контроля доступа (RBAC).

## Архитектурная схема (Workflow)

```text
Клиент (Postman / Frontend)
        |
        | 1. POST /login {username, password}
        v
IAM Proxy (FastAPI)  <--- (добавляет client_id и client_secret)
        |
        | 2. POST /token (grant_type=password)
        v
Keycloak (IdP)       <--- (проверяет хэш пароля в своей БД, подписывает JWT)
        |
        | 3. JWT (access + refresh)
        v
IAM Proxy (FastAPI)  <--- (отдает токен клиенту)
        |
        | 4. JWT клиенту
        v
Клиент

Далее:
Клиент -> GET /me (Authorization: Bearer <access_token>)
        -> IAM Proxy (берет публичный ключ из Keycloak, проверяет подпись JWT, извлекает роли)
           и возвращает identity-контекст.
